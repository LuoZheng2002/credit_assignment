# Problem to be solved and related work
This repo tries to find a fine credit assignment strategy as opposed to trajectory-level uniform reward / penalty.

Currently there are related works about credit assignment strategies:

## paper_references/1_igpo.pdf
This paper determines a reward to a step based on whether this step increases the model's "confidence" corresponding to the ground truth answer (its probability of outputting the answer token same as the ground truth answer). The limitation is that we need the assumption that model's "confidence" is correlated with the effectiveness of a step; we need to peek the ground truth answer instead of relying on model's own ability to determine the correctness of a step; the idea is only applicable to web search problems where the model has a chance to get more and more sure about an answer after each step of search and reasoning, but not applicable to problems like math where it is impossible to guess the final answer without calculating the exact value at the last step.

## paper_references/2_scar.pdf
This paper determines a reward to a piece of the reasoning process by removing it from the context and find the difference in reward given by a reward model. However, it is not justified whether the reward model can give a stable score estimate on a partial context since it is not directly trained on it.

## paper_references/3_grpo_lambda.pdf
This paper gives different reward importance to tokens based primarily based on their distance to the answer token. The closer the token is to the answer token, the more important the token is. The idea is intuitive, but it is too general, without case-by-case working principle insights, and may not be practically valid beyond theoretical proof.

## paper_references/4_capo.pdf
This paper uses an LLM to do "manual" credit assignment, which is a very intuitive idea. However, there are concerns reported by reviewers about the additional training cost induced by the extra LLM inference for credit assignment, and it is not scalable to rely on a capable GenPRM.

## paper_references/5_int.pdf
This paper mainly uses same-model-generated revised trajectory by comparing the self-generated wrong trajectory and reference trajectory (generated by Gemini), to do SFT on the model itself. This is essentially doing SFT on better model's trajectory (learning from teacher), but with the answer style to adhere to the original model. After that, standard RL is adopted to reinforce the already learned good trajectories.

This idea is not bad, but it still relies on learning from a better teacher instead of exclusively exploiting the model's own potential. Nevertheless, the paper states their method generalizes well to unseen test sets. 

The question remaining is: how can we do better based on this? Can it be used in a multi-turn agentic system?

The learned strategy is implicit. Can we make it explicit by introducing a verifier?

## paper_references/6_spark.pdf
This paper introduces a reference-free (without relying on ground-truth answers) reinforcement learning pipeline. It trains a PRM by collecting data and verification from the same model, and then train the model with PRM using GRPO.

This paper is good in that it is reference-free. The idea is standard, but like CAPO, it requires extra RL cost by introducing an LLM for credit assignment.

## paper_references/7_genprm.pdf
This paper trains a dedicated verifier / critic, potentially for credit assigment for training other models.

## paper_references/9_prints.pdf
Agentic credit assignment problem, may need another look in the future.

# Current plan
We mainly use paper_references/5_int.pdf as the algorithm and apply it to an agentic system that is able to write python code (and optionally search) to solve all kinds of complex problems that may require multi-step tool-invocation + reasoning.

For the agentic system, we set its operation mode to have clear boundaries between turns, and each turn involves \[reasoning, execution, reasoning\] and \[verification\]. We train two different roles for execution and verification.

## Selling points
* reference-free (which is similar to paper_references/6_spark.pdf), no better model or ground truth is needed
* step-level credit assignment (hopefully through the verifier)
* tool-calling, that can use python code (and optionally search) to solve problems. (same as agent flow)
* agentic system: long horizon reasoning, unentangled roles, trimmable context
* cost-effective: no inference time scaling needed, linear reasoning process
* direction choice robustness: if finding the current direction not promising, the model changes direction automatically, without the need for rule-based trimming or trajectory sampling.
* (optional) more fine-grained verifier output other than binary promising / not promising, but multifacet like "too much manual calculation, use more systematic approach", "lack answer verification", "wrong reasoning process; hallucination spotted", etc.

## Setup
* One 7B model serving two roles for now, because of harware limitation.
* Python code execution only for now, no search involved.
* Problems to be solved: math, science and engineering direction, close-ended

## Procedural Plan
1. Set up the agentic system and make it work on the datasets to see what problems can occur.
2. Most likely the base model does not adapt to the agentic system and need behavioral alignment, in which case add more prompts to see if it gets better. If not, may require GPT to generate samples and SFT. If more prompts work, defer the SFT and focus on reasoning process problems.
3. If problems cannot be solved due to behavioral misalignment, adjust prompts to include task-specific hints and see if some of the existing problems can be solved, so that no reference trajectory is needed.
4. Potential RL pan: train executor and verifier at the same time.
    * Verifier should have a good prior (model's inherent capability)
    * Initially the executor never listens to the verifier (mask verifier output out from executor's context). For each rollout, see if the verifier's prediction aligns with the outcome; train the verifier.
    * Train the executor based on both the final outcome and verifier's verdict, the blending is based on verifier's growing capability.
    * Executor will begin to listen to the verifier (less and less masking) and change plan, in which case the verifier's correctness is based on the reward improvement from executor not listening to the verifier and executor listening to the verifier. The two scenarios are explicitly played out to avoid training noises.
    * If the executor is hesitant about whether to listen to the verifier, then it is a good opportunity to reward / penalize the executor for listening / not listening to the verifier, because it's on-policy.
5. The biggiest concern is that the change of plan is not sufficient when the model lacks advanced mindset required for solving hard problems, in which case, we prioritize trying if adding task-specific prompts (manually injecting general mindset knowledge) helps.

# How To Work (IMPORTANT)
## When writing python code
* The overall style is to expose a problem early instead of hiding it or allowing a suboptimal run with unfavorable fallbacks. You'd rather not handle a potential vulnerability that may cause a runtime crash at all, than to intentionally hide it. A better act when spotting a vulnerability is to add assert statements before it to communicate the semantic assumption.
* The following "fallback mechanism" refers to the act of patching a scenario that is not expected by the program semantic. Intentional branching on expected scenarios is exempted from the following. Do not add fallback mechanism unless the user has explicitly requested or approved it. If you think a fallback mechanism is idiomatic or very helpful in certain scenarios, explicitly recommend it to the user and ask for approval. Fallback mechanism can include implicit ones like my_dict.get('key', None) or my_dict.get('key', []), in this case, prefer my_dict['key'] to let the program crash naturally if 'key' is not found.
* Prefer assert statement over if + raise statement.
* Make all function arguments mandatory without a default value, unless approved by the user for not to, in which case an inline comment is needed to explain the reason. If there is a recommended default value, like for hyperparameters, state it in the form of an inline comment. Do not make arguments optional (via "| None") unless the user explicitly says so or you're sure it agrees with the context semantic. Add inline comment explaining the necessity of all optional arguments.
* For any object used in a class instance, either instantiate it within the class or pass it to the class through constructor or other functions, but do not allow both to possibly happen. If you think it is necessary, ask for user's approval before implementing it, and leave a comment explaining it.
* If you find currently in the code there are places violating the above rules and without comments explaining the reason, inform the user after the current task is done and revise them after receiving approval.
